<p><strong>Key takeaways</strong></p>
<ul>
<li>Assessing a DDoS attack is not just about asking "how big is the attack traffic?" You also need to know which resource the attack is consuming: bandwidth, connections, or application processing capacity.</li>
<li>Volumetric Attacks are measured in BPS and aim to saturate bandwidth. Protocol Attacks are measured by PPS, SYN Rate, and Concurrent Connections, and aim to exhaust connection resources.</li>
<li>L7 and CC Attacks send Requests that fully comply with the HTTP Protocol. The traffic is not necessarily large, but it can be concentrated on high-cost Endpoints such as Login, Search, and APIs.</li>
<li>At L7, a single Request is almost impossible to tell apart from a real user or a malicious Bot. You need Request Frequency, Fingerprint, Session, and Behavior data to understand "what is this Client actually doing?"</li>
</ul>
</div>
<p>When businesses talk about DDoS protection, the first things that come to mind are usually bandwidth and scrubbing capacity: how many Gbps can it absorb? Can it handle Tbps-scale floods?</p>
<p>Those questions matter, but they no longer describe the full DDoS risk. Beyond Volumetric Attacks that saturate bandwidth, an attack can also drain TCP connections, Web Servers, APIs, or Database resources.</p>
<p>At Layer 7 (L7) in particular, attack traffic is not always especially large. A flood of normal-looking HTTP Requests can steadily drain application resources through high-cost Endpoints such as Login, Search, and APIs.</p>
<p>So assessing a DDoS attack is not just about asking "how big is the attack traffic?" You also need to answer: <strong>which resource is the attack consuming?</strong></p>
<h2>What Is a DDoS Attack?</h2>
<p>DDoS (Distributed Denial of Service) is an attack that uses traffic or requests from many distributed sources to exhaust a target's resources, so that legitimate users can no longer access the service.</p>
<p>But different DDoS attacks consume different resources. From the network layer to the application layer, common DDoS attacks fall into three broad categories:</p>
<ol>
<li>Volumetric Attack: traffic-based attacks</li>
<li>Protocol / L3-L4 Attack: protocol-based attacks</li>
<li>Application / L7 Attack: application-layer attacks</li>
</ol>
<p>On top of that, at the application layer, Automated Bot Traffic can also overlap with HTTP Floods, CC Attacks, and API Abuse.</p>
<div class="table-wrap">
<table>
<thead>
<tr><th>Attack type</th><th>Primary target</th><th>Common examples</th><th>Key metrics to watch</th></tr>
</thead>
<tbody>
<tr><td>Volumetric Attack</td><td>Network Bandwidth</td><td>UDP Flood, DNS Amplification</td><td>BPS</td></tr>
<tr><td>Protocol / L3-L4 Attack</td><td>TCP Connections, Network Resources</td><td>SYN Flood, Connection Exhaustion</td><td>PPS, Concurrent Connections</td></tr>
<tr><td>Application / L7 Attack</td><td>Web Servers, APIs, Applications, Databases</td><td>HTTP Flood, CC Attack, API Flood</td><td>RPS, URI / API Endpoint, HTTP Status</td></tr>
<tr><td>Automated Bot Traffic*</td><td>Business Logic, Accounts, APIs</td><td>Login Abuse, Scraping, Automated Requests</td><td>Fingerprint, Session, Behavior</td></tr>
</tbody>
</table>
</div>
<p><small>* Automated Bot Traffic is not necessarily DDoS in itself, but at the application layer it can overlap with HTTP Floods, CC Attacks, and API Abuse.</small></p>
<h2>Type 1: Volumetric Attacks Aim to Saturate Bandwidth</h2>
<p>The Volumetric Attack is the most intuitive type of DDoS attack. Its goal is simple: flood the target's network bandwidth with so much traffic that legitimate user traffic cannot get through.</p>
<p>Common methods include:</p>
<ul>
<li>UDP Flood</li>
<li>DNS Amplification</li>
<li>Reflection / Amplification Attack</li>
</ul>
<p>These attacks are usually measured in BPS (Bits Per Second). When BPS spikes abnormally in a short period, approaching or even exceeding the bandwidth the network can carry, the result can be:</p>
<p><strong>Packet Loss → Rising Latency → Connection Timeout → Service becomes unreachable</strong></p>
<p>The defining trait of a Volumetric Attack, then, is using sheer traffic volume to consume network capacity. The flip side is that bandwidth not being maxed out does not mean you are free of DDoS, because the next type of attack targets an entirely different resource.</p>
<h2>Type 2: Protocol Attacks Can Take a Service Down Without Saturating Bandwidth</h2>
<p>Protocol Attacks do not target bandwidth itself. They target network protocols and connection resources. One of the classic examples is the SYN Flood.</p>
<p>A normal TCP connection requires a three-way handshake:</p>
<ol>
<li>The Client sends a SYN</li>
<li>The Server replies with a SYN-ACK</li>
<li>The Client returns an ACK, and the Connection is Established</li>
</ol>
<p>In a SYN Flood, however, the attacker sends huge numbers of SYN Requests without ever completing the connection.</p>
<p>The Server has to temporarily hold on to the Connection State for each of these unfinished connections. As half-open connections keep piling up, they can exhaust the connection resources of the Server, Firewall, Load Balancer, or other intermediate devices, leaving legitimate users unable to establish new Connections.</p>
<p>That is why BPS alone is not enough for this kind of attack. Metrics such as PPS (Packets Per Second), Concurrent Connections, and SYN Rate are often far more telling.</p>
<p>Put simply: Volumetric Attacks are about "how much traffic is there," while Protocol Attacks require you to watch "how many packets and connections the system is handling."</p>
<h2>Type 3: Application Layer / L7 Attacks Are Not Always Large, but They Can Be Costly</h2>
<p>At Layer 7, DDoS attacks become far more complex, because what the attacker sends is not necessarily an abnormal packet. It may be a Request that fully complies with the HTTP Protocol. For example:</p>
<pre><code class="hljs language-http">GET /product/123
POST /login
GET /api/search
</code></pre>
<p>From the Network Layer's perspective, all of these may look like normal TCP / HTTPS Traffic.</p>
<p><strong>The real question is: how much does it cost the server to process each Request?</strong></p>
<p>For instance, a single Login Request may involve:</p>
<p><strong>Account validation → Database Query → Token Verification → Session creation → Response</strong></p>
<p>A single Search API call may involve a Database Query, a Search Index, or other Backend Computation.</p>
<p>If large numbers of Requests keep hitting these high-cost Endpoints, CPU, Database Connections, Application Threads, or API Resources can be heavily tied up, even when total Bandwidth shows no obvious increase.</p>
<p>This is what makes Application Layer DDoS so troublesome: the attack traffic can look almost identical to real users.</p>
<h2>What Is a CC Attack, and Why Is It an L7 Attack?</h2>
<p>CC Attack (Challenge Collapsar) is a term commonly used for application-layer attacks that send large volumes of HTTP Requests to continuously drain Web Server or Application Resources.</p>
<p>The biggest difference from a traditional high-volume DDoS attack is this: <strong>a Volumetric Attack mainly consumes network capacity, while a CC Attack is closer to consuming the service's processing capacity.</strong></p>
<p>For example, an attacker may repeatedly request:</p>
<ul>
<li><code>/login</code></li>
<li><code>/search</code></li>
<li><code>/api/query</code></li>
<li><code>/product</code></li>
<li>Dynamic Page</li>
<li>Uncached Content</li>
</ul>
<p>Say a single <code>/login</code> Request is only a few KB, so its impact on Bandwidth is minimal. But if every Request requires a Database Query, Authentication, or other Application Logic, then as requests pile up, it is the backend resources that actually get exhausted.</p>
<p>So a website with plenty of bandwidth is not necessarily able to withstand a large volume of CC / L7 Requests. This is also why RPS (Requests Per Second) is usually far more meaningful than BPS alone when identifying a CC Attack.</p>
<h2>BPS, PPS, RPS: What Should You Look at During an Attack?</h2>
<p>In many DDoS incidents, the first step is not to start blocking IPs right away. It is to determine which layer of resources is actually behaving abnormally.</p>
<div class="table-wrap">
<table>
<thead>
<tr><th>What you observe</th><th>Check first</th><th>Likely attack type</th></tr>
</thead>
<tbody>
<tr><td>Sudden surge in Bandwidth</td><td>BPS</td><td>Volumetric Attack</td></tr>
<tr><td>Abnormal increase in Packet count</td><td>PPS</td><td>L3/L4 Attack</td></tr>
<tr><td>Large increase in SYN / Connections</td><td>Connection / SYN Rate</td><td>Protocol Attack</td></tr>
<tr><td>Sudden surge in HTTP Requests</td><td>RPS</td><td>HTTP Flood / CC</td></tr>
<tr><td>Abnormal concentration on Login / Search / API</td><td>URI / API Endpoint</td><td>L7 / API Abuse</td></tr>
<tr><td>Many different IPs showing similar behavior</td><td>Fingerprint / Session / Behavior</td><td>Automated Bot</td></tr>
</tbody>
</table>
</div>
<p>In short:</p>
<ul>
<li>BPS tells you how much traffic the network is carrying</li>
<li>PPS tells you how many packets the network is processing</li>
<li>RPS starts to tell you how many requests the application is handling</li>
</ul>
<p>At L7, no single one of these metrics is enough to fully characterize an attack.</p>
<h2>Why Are CC / L7 Attacks Harder to Identify Than Traditional DDoS?</h2>
<p>Imagine three Requests:</p>
<ul>
<li>A real user: <code>GET /product/123</code></li>
<li>An ordinary Crawler: <code>GET /product/123</code></li>
<li>A malicious Bot: <code>GET /product/123</code></li>
</ul>
<p>Looking at a single HTTP Request, there may be no visible difference between them. So at L7, a protection system cannot just ask "is this IP on a blocklist?" It also needs to look at:</p>
<ul>
<li>Request Frequency and Request Interval</li>
<li>URI / API Endpoint</li>
<li>IP / ASN Distribution</li>
<li>User-Agent, TLS / Device Fingerprint</li>
<li>Cookie / Session, Navigation Pattern, and Historical Behavior</li>
</ul>
<p>For example, a Client requesting a product page at perfectly identical intervals, or many different IPs producing highly consistent Request Sequences, can be far more revealing than IP Reputation alone.</p>
<p>And when Automated Traffic goes further, combining Distributed IPs, varied User-Agent / Client characteristics, varied Request Intervals, and varied APIs / Endpoints, or even mimicking ordinary browsing, the effectiveness of a plain IP Blocklist drops even more.</p>
<p>At L7, the question shifts from "where is this Request coming from?" to "what is this Client actually doing?"</p>
<p>Keep in mind that a Bot is not the same thing as DDoS. Search engine Crawlers, Monitoring Services, and other legitimate automated tools can also be Automated Traffic. What really needs to be identified is whether this automated behavior is generating large volumes of abnormal Requests, Login Abuse, Scraping, API Abuse, or other application and business risks.</p>
<p>The challenge at L7 is not just spotting abnormal packets. It is spotting abnormal behavior.</p>
<h2>As Attacks Look More Like Normal Traffic, How Do You Tell Them Apart and Stop Them?</h2>
<p>From Volumetric and Protocol to L7, different DDoS attacks target different resources: <strong>bandwidth → connections → application processing capacity</strong>.</p>
<p>That means businesses can no longer watch only BPS and PPS. Monitoring has to extend to RPS, API Endpoints, Sessions, Fingerprints, and Behavior. Once an attack reaches L7, malicious Requests may show no obvious difference from real users at all.</p>
<p>Which raises the next question: if different attacks happen at different Layers, is a single type of protection really enough?</p>

<h2>FAQ</h2>
<h3>What are the main types of DDoS attacks?</h3>
<p>From the network layer up to the application layer, common DDoS attacks fall into three broad categories: Volumetric Attacks (which consume bandwidth), Protocol / L3-L4 Attacks (which exhaust TCP connections and network resources), and Application / L7 Attacks (which drain Web Server, API, and Database resources). At the application layer, Automated Bot Traffic can also overlap with HTTP Floods, CC Attacks, and API Abuse.</p>
<h3>How is a CC Attack different from a traditional high-volume DDoS attack?</h3>
<p>A Volumetric Attack mainly consumes network capacity. A CC Attack sends large numbers of HTTP Requests to high-cost Endpoints such as /login, /search, and APIs, consuming the service's processing capacity instead. A single request may be only a few KB, but each one triggers a Database Query or authentication, and together they can saturate backend resources.</p>
<h3>During an attack, should I look at BPS, PPS, or RPS?</h3>
<p>BPS shows how much traffic the network is carrying and is the key signal for Volumetric Attacks. PPS, along with SYN Rate and Concurrent Connections, shows how many packets and connections the system is handling, which helps identify Protocol Attacks. RPS shows how many requests the application is taking on, which helps identify HTTP Floods and CC Attacks. At L7, you also need URI, Fingerprint, Session, and Behavior data to get the full picture.</p>
<h3>If bandwidth is not maxed out, does that mean there is no DDoS attack?</h3>
<p>Not necessarily. A Protocol Attack can exhaust the connection resources of a Server, Firewall, or Load Balancer with masses of half-open connections, and an L7 attack can concentrate on draining application resources with normal-looking HTTP Requests. Neither has to cause a noticeable spike in bandwidth.</p>
<h3>Is all bot traffic DDoS?</h3>
<p>No. Legitimate automated tools such as search engine Crawlers and Monitoring Services also count as Automated Traffic. What really needs to be identified is whether automated behavior is generating large volumes of abnormal Requests, Login Abuse, Scraping, API Abuse, or other business risks.</p>
