<p><strong>Key takeaways</strong></p>
<ul>
<li>After SDK integration, the client no longer connects directly to the origin. It first obtains a proxy IP and port from the scheduling platform, and an edge node forwards the connection to the origin. Proxy addresses change dynamically and should be re-fetched after every reconnect.</li>
<li>By default the origin sees the proxy node IP. When you need the real client IP, there are three modes: Proxy Protocol, TOA, and API. If the origin supports Proxy Protocol, choose that first.</li>
<li>The SDK does not add, modify, or remove headers; it passes them through as-is. Custom fields such as X-App-Version must be added by the client.</li>
<li>Host header, origin firewall policy, heartbeats and health checks, and HTTPS certificate policy should all be confirmed by both sides during the POC.</li>
<li>For acceptance, first verify that outbound connections show the proxy address rather than the origin IP, then run a small-percentage canary release for 2 to 3 days before rolling out to everyone.</li>
</ul>
</div>
<p>When integrating a Security Acceleration SDK, the part that usually causes trouble is not the initialization function. It is the details the proxy architecture introduces: Does the origin see the node IP or the player IP? Can we use a Real IP header? Can the SDK add custom headers automatically? After a disconnect, does the client keep using the same proxy address?</p>
<p>If these questions are not settled during the POC, the SDK may compile cleanly into the app and still cause gaps in login verification, risk control, log analysis, IP blocking, or load balancing. The sections below walk through them in the order of the actual integration flow.</p>
<ul>
<li>Does the origin see the node IP or the real player IP? How do we pass the real IP through?</li>
<li>What are Proxy Protocol, TOA, and API, and which one should I choose?</li>
<li>Can the SDK automatically add custom headers (such as X-App-Version) for me?</li>
<li>Why do I need to fetch a new proxy address after reconnecting? Can I reuse the old one?</li>
</ul>
<h2>How does the SDK establish a secure proxy tunnel?</h2>
<p>Once integration is complete, the client no longer connects directly to the origin. It first obtains a proxy IP and port through the SDK, and an edge node forwards the connection to the origin. The basic flow is:</p>
<ol>
<li>The client initializes the SDK with its AccessKey and device identification data.</li>
<li>The SDK requests an available proxy IP and port from the scheduling platform.</li>
<li>The client establishes a connection using the proxy address it received.</li>
<li>The edge node forwards the original business request to the origin configured in the console.</li>
</ol>
<p>This model hides the origin IP and adjusts paths based on network quality, node health, and risk signals. Because the proxy address can change dynamically, the client should call <code>getServerIPAndPort</code> again for every new request, after every reconnect, and after the device wakes from lock screen, rather than caching an old IP and port for long periods.</p>
<p><img src="/images/blog/sdk-proxy-connection.webp" alt="SDK proxy connection architecture: the client app first obtains a proxy IP and port from the scheduling platform (control plane), then connects directly to the proxy address, and the edge node forwards traffic to the enterprise origin; the real IP can be passed via Proxy Protocol (recommended), TOA, or API; the whole flow does not depend on local DNS resolution, so the client still obtains a correct proxy address even when DNS is hijacked"></p>
<h2>What needs to be configured in the console before integration?</h2>
<p>Customers can configure forwarding rules self-service in the console. Before formal configuration, we recommend taking inventory of the business domains, ports, protocols, and origin addresses that the SDK needs to protect, and isolating the origin from other unprotected services.</p>
<div class="table-wrap">
<table>
<thead>
<tr><th>Setting</th><th>Description</th></tr>
</thead>
<tbody>
<tr><td>Virtual domain</td><td>Used internally to identify forwarding rules. It needs no public DNS resolution and no ICP filing, and it cannot become a hijacking target</td></tr>
<tr><td>Forwarding port</td><td>Used by the SDK to distinguish different services, for example 80, 443, or game service ports</td></tr>
<tr><td>Load balancing</td><td>Choose Round-Robin, or use IP Hash so that the same IP is preferentially routed to the same origin</td></tr>
<tr><td>Origin configuration</td><td>Enter the actual origin IP and service port; avoid exposing the origin IP directly through other services</td></tr>
</tbody>
</table>
</div>
<h2>Is a Real IP header supported? Clarify the actual need first</h2>
<p>Once the SDK forwards connections through proxy nodes, the network source the origin sees by default may be the proxy node rather than the end user's real IP. So if login risk control, geolocation, log auditing, or blocking policies depend on the real client IP, you need to configure a way to pass the real IP through.</p>
<p>Three modes are currently supported for obtaining the real client IP:</p>
<div class="table-wrap">
<table>
<thead>
<tr><th>Mode</th><th>When to use it</th><th>Implementation notes</th></tr>
</thead>
<tbody>
<tr><td>Proxy Protocol</td><td>The origin or load balancer (such as Nginx or ALB) supports it</td><td>Carries the original source IP and port at the connection layer (L4); the origin must parse the PROXY protocol header. Recommended first choice</td></tr>
<tr><td>TOA (TCP Option Address)</td><td>Requires kernel module support on the OS or load balancer</td><td>Carries the client IP in a TCP option field; the origin needs the matching kernel module to read it</td></tr>
<tr><td>API</td><td>Neither of the above can be supported directly</td><td>The business system queries the platform via API for the real client IP of a given connection; suited to legacy architectures or special protocols</td></tr>
</tbody>
</table>
</div>
<p>In other words, "supports obtaining the real IP" does not mean "the SDK will add an arbitrary Real IP header." Which method you actually use should depend on the origin server, load balancer, protocol type, and existing logging and risk control systems. If the origin supports Proxy Protocol, we recommend choosing it first, since the architecture is usually the most straightforward.</p>
<h3>Extra: Nginx configuration example (Proxy Protocol)</h3>
<p>If the origin runs Nginx with Proxy Protocol enabled, add <code>proxy_protocol</code> to the <code>listen</code> directive and use <code>real_ip_header proxy_protocol</code> to read the real IP from the PROXY protocol header:</p>
<pre><code class="hljs language-nginx">http {
    # Log the real client IP
    log_format main '$proxy_protocol_addr - $remote_user [$time_local] "$request"';

    server {
        listen 80 proxy_protocol;
        listen 443 ssl proxy_protocol;

        # Trusted proxy sources (in production, restrict this to the SDK edge node IP ranges)
        set_real_ip_from 0.0.0.0/0;
        # Read the real IP from the PROXY protocol header and override $remote_addr
        real_ip_header proxy_protocol;

        access_log /var/log/nginx/access.log main;
    }
}
</code></pre>
<h2>Can I add custom headers self-service?</h2>
<p>The SDK console currently does not offer a feature for adding custom headers. The SDK's operating principle is to pass the headers in the client's original request through to the origin unchanged, without proactively adding, modifying, or removing any header.</p>
<p>By design, the SDK focuses on secure proxying and traffic scheduling and does not intervene in application-layer business logic. This avoids naming conflicts between the SDK and business headers and reduces coupling for future maintenance.</p>
<p>If your business needs X-App-Version, X-Device-ID, X-Channel, or other custom fields, the client should add them when sending the original request. The SDK forwards existing headers along with the request but is not responsible for generating or rewriting their content.</p>
<p>To avoid confusion: passing the real IP is a source identification problem in the proxy architecture, while custom headers are business data defined by the application itself. They live at different layers of responsibility and are configured in different ways.</p>
<h2>What else is easy to overlook during integration?</h2>
<h3>Origin configuration notes</h3>
<ul>
<li>HTTP requests must preserve the correct Host header; otherwise the origin's virtual hosts may fail to determine the target service.</li>
<li>SDK nodes are scheduled dynamically, so do not restrict the origin with a fixed node IP allowlist alone. The origin firewall policy should be designed jointly during the POC.</li>
<li>Heartbeats and business health checks are implemented at the application layer. The SDK does not judge origin service status on the business's behalf.</li>
</ul>
<h3>Android notes</h3>
<ul>
<li>Confirm compatibility between the ARM64-v8a, armeabi-v7a, x86, and other architectures and any other third-party SDKs.</li>
<li>Add the specified ProGuard rules to prevent obfuscation from breaking the SDK.</li>
</ul>
<h3>iOS notes</h3>
<ul>
<li>When integrating as a Framework, libz must be linked.</li>
<li>After waking from lock screen or switching networks, call <code>getServerIPAndPort</code> again to obtain a proxy address.</li>
</ul>
<h3>HTTPS and certificates</h3>
<ul>
<li>The HTTPS and certificate validation policy should be confirmed by both technical teams during the POC to ensure it matches the app's existing security design and to avoid SSL handshake failures.</li>
</ul>
<h2>How should testing and acceptance be done?</h2>
<ol>
<li>Use a packet analysis tool to confirm that the app's outbound connections show the proxy address rather than exposing the origin IP directly.</li>
<li>Confirm in your business systems and logs that the client IP obtained is the real user address, not the proxy node IP.</li>
<li>Test Wi-Fi, 4G/5G, network switching, reconnecting after loss of connectivity, lock screen, and resuming from background.</li>
<li>Check login, long-lived connections, API responses, packet integrity, and load balancing results.</li>
<li>Run a small-percentage canary release for 2 to 3 days first, collect error logs and user feedback, then gradually roll out to everyone.</li>
</ol>
<h2>Conclusion: clarify proxy responsibilities first, and integration goes smoothly</h2>
<p>The core of the Security Acceleration SDK is a protected, schedulable proxy tunnel, not a replacement for all application-layer logic. Real IP, headers, heartbeats, certificates, and origin security policy are shared responsibilities of the SDK, the client, and the origin.</p>
<p>The SDK's core value is not just the secure proxy tunnel. It also bypasses DNS resolution at the endpoint, eliminating the impact of DNS hijacking on business connections at the source, and scheduling policies can be pushed remotely in real time so routing can be adjusted without waiting for an app release. Whether these capabilities deliver as intended depends on how complete the architecture design is during integration, and Real IP, headers, and origin security policy are exactly the details most often overlooked.</p>
<p>Companies that take inventory of protocols, origin architecture, Real IP use cases, and custom header requirements before the POC greatly reduce the chance of discovering after integration that risk control, logging, or verification flows are incompatible.</p>
<h2>FAQ</h2>
<h3>My origin supports Proxy Protocol. Which real IP mode should I choose?</h3>
<p>Prefer Proxy Protocol. It carries the original source information at the connection layer, but you still need to confirm that the origin or load balancer has it correctly enabled and is parsing it.</p>
<h3>Can I specify a different header to carry the real IP?</h3>
<p>The SDK can help you obtain the real client IP, but the standard supported methods are Proxy Protocol, TOA, and API. The SDK does not add arbitrary headers on its own. If your application needs custom headers, the client must add them to the original request.</p>
<h3>Does the SDK remove or modify existing headers?</h3>
<p>No. The SDK passes the headers from the client's original request through to the origin unchanged. It does not add, modify, or remove any of them.</p>
<h3>Why call getServerIPAndPort again for every new connection?</h3>
<p>Proxy addresses change dynamically based on node health, network quality, and scheduling policy. Fetching a fresh address prevents the client from continuing to use a node that has expired or is no longer suitable.</p>
<h3>Does the SDK handle heartbeats and origin health checks automatically?</h3>
<p>No. Heartbeat mechanisms and business-layer health checks must be implemented by the application. The SDK is responsible for secure proxying, scheduling, and connection forwarding.</p>
<h3>Does adopting the SDK affect HTTPS certificate validation?</h3>
<p>The SDK itself does not replace or terminate HTTPS certificates; certificate validation remains in the client's original code. However, if the origin only accepts traffic from specific source IPs, the SDK edge node IP ranges must be added to the allowlist (the platform provides the list). The exact certificate policy should be confirmed by both technical teams during the POC.</p>
