<p><strong>重点摘要</strong></p>
<ul>
<li>同一个网址，不一定代表相同的内容；若 CDN 将需要区分的请求视为相同，就可能把不适合共用的回应提供给客户。</li>
<li>CDN 快取污染（Cache Poisoning）是攻击者利用 CDN 与源站的判断落差，让受到操控的回应进入共用快取。</li>
<li>Cache Key 并非越复杂越好，涉及身分与授权的内容，也不能仅靠增加快取栏位就认定安全。</li>
<li>源站的 private、no-store、no-cache 快取指示意义不同，三者不能混用，也要确认 CDN 规则是否覆写源站设定。</li>
<li>看到 HIT 只能证明快取被使用，仍需透过分阶段与跨账号验证，确认回传内容正确。</li>
</ul>
</div>
<p>网站导入 CDN 后，通常会透过快取降低回源流量、缩短载入时间，让不同地区的使用者更快取得内容。然而，当网站同时提供多语系、会员服务与个人化资讯时，快取设定也需要配合应用程式的实际行为调整。</p>
<p>同一个网址，不一定代表相同的内容。若 CDN 将原本需要区分的请求视为相同，就可能把不适合共用的回应提供给客户。当攻击者进一步利用这类判断落差，让受到操控的回应进入共用快取，就可能形成 <strong>CDN 快取污染（Cache Poisoning）</strong>。</p>
<p>因此，评估 CDN 快取效果时，除了速度与命中率，也需要确认：<strong>哪些内容可以被共用，以及 CDN 的判断是否与源站一致。</strong></p>
<h2>为什么同一个网址，可能需要回传不同内容？</h2>
<p>以跨境电商网站为例，使用者开启相同的商品页面，看到的内容可能因情境而有所不同：</p>
<ul>
<li>语系差异：中国与日本使用者选择不同语系，页面文字随之改变。</li>
<li>币别调整：使用者切换计价币别，商品价格与促销资讯跟着调整。</li>
<li>个人化资讯：会员登入后，页面出现专属折扣价、账户资讯或购物车状态。</li>
</ul>
<p>这些差异可能来自 URL 路径、Query String、Cookie、HTTP Header，或应用程式判断的登入状态。</p>
<p>从源站的角度来看，这些是需要分别处理的请求；但如果 CDN 只依照部分资讯区分快取，就可能将不同版本合并。</p>
<p>需要注意的是，显示错误语系或币别，不一定代表遭到攻击；它也可能只是快取策略与业务逻辑没有对齐。<strong>因此，在追求快取效率之前，必须先确认内容的共用范围。</strong></p>
<h2>CDN 如何决定能否使用同一份快取？</h2>
<p>CDN 通常透过 <strong>Cache Key（快取键）</strong>，识别请求所对应的快取内容。Cache Key 可以理解为查找快取的索引，实际组成则取决于平台与设定，可能涉及网域、路径、Query String 或指定的请求栏位。</p>
<p>例如，网站透过以下网址提供不同币别：</p>
<div class="table-wrap">
<table>
<thead>
<tr><th>请求网址</th><th>源站预期回传内容</th></tr>
</thead>
<tbody>
<tr><td>/products/item-a?currency=CNY</td><td>人民币价格</td></tr>
<tr><td>/products/item-a?currency=JPY</td><td>日圆价格</td></tr>
</tbody>
</table>
</div>
<p>如果 CDN 忽略 currency，源站却依照这个参数产生不同内容，就可能发生版本混用。</p>
<p>快取污染则进一步涉及攻击者操控回应。例如，应用程式信任了外部传入的 Header，依其内容产生页面连结；但 CDN 没有区分这个 Header 的差异。当受到操控的页面被快取，后续正常访客也可能取得同一份内容。</p>
<p>处理方式需要依应用需求决定：移除不必要的输入影响、让快取策略正确区分内容，或让该回应略过共用快取。</p>
<p><strong>Cache Key 并非越复杂越好。</strong> 将所有 Cookie 与参数纳入，可能产生大量低重用性的快取版本；涉及身分与授权的内容，也不能仅靠增加快取栏位就认定安全。</p>
<h2>快取设定需要确认哪些资讯？</h2>
<p>设定之前，建议先依应用路径整理“哪些资讯会改变回应”，再决定共用与排除规则。</p>
<div class="table-wrap">
<table>
<thead>
<tr><th>请求资讯</th><th>需要确认的问题</th><th>预期内容与设定方向</th></tr>
</thead>
<tbody>
<tr><td>路径 Path</td><td>是公开资源、会员页面，还是交易端点？</td><td>商品图片可评估共用；账户与结账内容应明确限制共用快取。</td></tr>
<tr><td>Query String</td><td>参数是否影响语系、币别、搜寻条件或存取权限？</td><td>保留有意义的内容差异；追踪参数需确认不影响回应后，才评估忽略。</td></tr>
<tr><td>Cookie</td><td>是否改变会员价格、购物车或个人化资讯？</td><td>公开内容与个人化内容分开处理，避免不同使用者共用敏感回应。</td></tr>
<tr><td>Header</td><td>是否参与语系选择、转址或内容生成？由谁设定？</td><td>确认必要栏位、可信来源与处理方式，避免直接信任用户端提供的代理资讯。</td></tr>
<tr><td>预期内容</td><td>相同条件下，哪些部分应一致？哪些必须隔离？</td><td>建立可比较的验收标准，涵盖本文、状态码、回应 Header 与转址位置。</td></tr>
</tbody>
</table>
</div>
<p>源站的快取指示也需要一并检查。依 HTTP 快取规范，private 限制共用快取储存回应，no-store 要求不储存，而 no-cache 允许储存，但重用前必须验证，三者不能混用。</p>
<p>部署时还要确认 CDN 规则是否覆写源站设定，并实测 Vary、Cookie 与授权请求的处理结果。不能只因档名看起来像静态资源，就认定内容适合公开共用。</p>
<h2>如何验证快取设定？</h2>
<p>验收应同时检查效能与内容正确性。建议在隔离的测试网域或授权环境中，使用测试账号与合成资料，依序比较三个阶段：</p>
<div class="table-wrap">
<table>
<thead>
<tr><th>验证阶段</th><th>检查内容</th></tr>
</thead>
<tbody>
<tr><td>源站回应</td><td>不同语系、币别与账号，是否取得预期内容？</td></tr>
<tr><td>CDN 首次回应</td><td>在确认没有既有快取后，回源结果是否与预期一致？</td></tr>
<tr><td>后续快取命中</td><td>另一个工作阶段取得的内容，是否仍符合其请求条件？</td></tr>
</tbody>
</table>
</div>
<p>每次测试先改变一个条件，才能厘清差异来自哪里。除了本文，也应比较状态码、转址位置、快取控制与平台提供的快取状态资讯。</p>
<p>跨账号检查尤其重要：账号 A 完成操作后，账号 B 与未登入访客不应取得 A 的个人资讯；公开且允许共用的内容，则应维持正确版本。</p>
<p>因此，<strong>看到 HIT 只能证明快取被使用，仍需要确认回传内容正确。</strong> 若浏览器与 CDN 结果不同，也要分别排查浏览器快取，避免混淆问题来源。</p>
<p>如果想进一步了解如何透过速度测试、Response Header 与快取命中率检查 CDN 的实际表现，也可以参考<a href="/zh/blog/is-your-cdn-actually-working/">〈CDN 真的有在工作吗？从速度测试到快取命中率的排查流程〉</a>。</p>
<p>若确认发生污染，应先限制受影响的快取行为、保留必要纪录，修正根因后再清除相关快取并复测，避免错误内容再次被写入。</p>
<h2>系统更新后，哪些设定需要重新检查？</h2>
<p>快取策略需要随应用演进。以下变更都应纳入检查：</p>
<div class="table-wrap">
<table>
<thead>
<tr><th>系统变更</th><th>重新确认的重点</th></tr>
</thead>
<tbody>
<tr><td>新增语系或币别</td><td>选择依据是否改变？不同版本是否仍能正确区分？</td></tr>
<tr><td>新增会员与个人化功能</td><td>原本公开的回应是否开始带入使用者资料？</td></tr>
<tr><td>API 改版</td><td>同一路径是否因 Token、参数或权限回传不同内容？</td></tr>
<tr><td>调整 Proxy、负载均衡或回源架构</td><td>Header 信任来源、Host 与 URL 解析是否一致？</td></tr>
<tr><td>修改 CDN 快取规则</td><td>规则优先顺序、排除范围与源站指示是否仍符合预期？</td></tr>
</tbody>
</table>
</div>
<p>尤其当边缘节点、代理与源站对编码、重复参数或路径正规化的解读不同时，原本的设定假设可能失效。应用与网路团队需要用同一组测试案例确认结果。</p>

<h2>常见问题</h2>
<h3>什么是 CDN 快取污染？</h3>
<p>当 CDN 将原本需要区分的请求视为相同，攻击者便可能利用这类判断落差，让受到操控的回应进入共用快取，后续正常访客也可能取得同一份内容，这就是 CDN 快取污染（Cache Poisoning）。</p>
<h3>Cache Key 是否越复杂越好？</h3>
<p>不是。将所有 Cookie 与参数纳入，可能产生大量低重用性的快取版本；涉及身分与授权的内容，也不能仅靠增加快取栏位就认定安全。应先依应用路径整理哪些资讯会改变回应，再决定共用与排除规则。</p>
<h3>看到 HIT 就代表快取设定正确吗？</h3>
<p>不一定。HIT 只能证明快取被使用，仍需要确认回传内容正确。验证时除了本文，也应比较状态码、转址位置、快取控制与平台提供的快取状态资讯，并检查不同账号与未登入访客是否取得各自应有的内容。</p>
<h3>系统更新后，哪些情况需要重新检查快取设定？</h3>
<p>新增语系或币别、新增会员与个人化功能、API 改版、调整 Proxy、负载均衡或回源架构，以及修改 CDN 快取规则时，都应重新确认快取策略是否仍符合预期。</p>
