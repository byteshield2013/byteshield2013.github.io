19:T462d,<div class="takeaways">
<p><strong>この記事のポイント</strong></p>
<ul>
<li>同じ URL でも、同じコンテンツとは限りません。区別すべきリクエストを CDN が同一とみなすと、本来共有すべきでないレスポンスが顧客に返されるおそれがあります。</li>
<li>CDN キャッシュポイズニング（Cache Poisoning）は、攻撃者が CDN とオリジンの判断のずれを突き、改ざんされたレスポンスを共有キャッシュに入り込ませる攻撃です。</li>
<li>Cache Key は複雑なほど良いわけではなく、本人確認や認可が関わるコンテンツは、キャッシュ項目を増やすだけでは安全とみなせません。</li>
<li>オリジンのキャッシュ指示である private、no-store、no-cache はそれぞれ意味が異なり、混同してはいけません。CDN のルールがオリジンの設定を上書きしていないかも確認が必要です。</li>
<li>HIT はキャッシュが使われたことを示すにすぎません。段階的な検証とアカウントをまたいだ検証で、返されるコンテンツが正しいかを確かめる必要があります。</li>
</ul>
</div>
<p>ウェブサイトに CDN を導入すると、通常はキャッシュによってオリジンへのトラフィックが減り、読み込み時間も短縮されるため、さまざまな地域のユーザーがより速くコンテンツを取得できるようになります。しかし、多言語対応、会員サービス、パーソナライズされた情報を同時に提供するサイトでは、アプリケーションの実際の動作に合わせてキャッシュ設定を調整する必要があります。</p>
<p>同じ URL でも、同じコンテンツとは限りません。本来区別すべきリクエストを CDN が同じものとして扱うと、共有すべきでないレスポンスが顧客に返されるおそれがあります。さらに攻撃者がこうした判断のずれを利用し、改ざんされたレスポンスを共有キャッシュに入り込ませると、<strong>CDN キャッシュポイズニング（Cache Poisoning）</strong> が発生する可能性があります。</p>
<p>そのため、CDN のキャッシュ効果を評価する際は、速度やヒット率だけでなく、<strong>どのコンテンツを共有してよいのか、そして CDN の判断がオリジンと一致しているか</strong> も確認する必要があります。</p>
<h2>なぜ同じ URL で異なるコンテンツを返す必要があるのか？</h2>
<p>越境 EC サイトを例に考えてみましょう。同じ商品ページを開いても、ユーザーの状況によって表示される内容は異なる場合があります。</p>
<ul>
<li>言語の違い：中国と日本のユーザーがそれぞれ異なる言語を選ぶと、ページのテキストもそれに応じて変わります。</li>
<li>通貨の切り替え：ユーザーが表示通貨を切り替えると、商品価格やプロモーション情報もあわせて変わります。</li>
<li>パーソナライズ情報：会員がログインすると、会員限定の割引価格、アカウント情報、カートの状態がページに表示されます。</li>
</ul>
<p>こうした違いは、URL パス、Query String、Cookie、HTTP Header、あるいはアプリケーションが判断するログイン状態から生じます。</p>
<p>オリジンから見れば、これらは個別に処理すべきリクエストです。しかし CDN が一部の情報だけでキャッシュを区別していると、異なるバージョンがひとつにまとめられてしまう可能性があります。</p>
<p>なお、誤った言語や通貨が表示されたからといって、必ずしも攻撃を受けているとは限りません。単にキャッシュポリシーとビジネスロジックがかみ合っていないだけということもあります。<strong>だからこそ、キャッシュ効率を追求する前に、コンテンツの共有範囲を明確にしておく必要があります。</strong></p>
<h2>CDN は同じキャッシュを使えるかどうかをどう判断するのか？</h2>
<p>CDN は通常、<strong>Cache Key（キャッシュキー）</strong> によって、リクエストに対応するキャッシュコンテンツを識別します。Cache Key はキャッシュを検索するためのインデックスと考えるとわかりやすいでしょう。具体的な構成はプラットフォームや設定によって異なり、ドメイン、パス、Query String、指定したリクエスト項目などが含まれます。</p>
<p>たとえば、あるサイトが次の URL で異なる通貨を提供しているとします。</p>
<div class="table-wrap">
<table>
<thead>
<tr><th>リクエスト URL</th><th>オリジンが返すべきコンテンツ</th></tr>
</thead>
<tbody>
<tr><td>/products/item-a?currency=CNY</td><td>人民元の価格</td></tr>
<tr><td>/products/item-a?currency=JPY</td><td>日本円の価格</td></tr>
</tbody>
</table>
</div>
<p>オリジンはこのパラメーターに応じて異なるコンテンツを生成しているのに、CDN が currency を無視していると、バージョンが混在してしまう可能性があります。</p>
<p>キャッシュポイズニングは、さらに攻撃者によるレスポンスの操作が関わるものです。たとえば、アプリケーションが外部から渡された Header を信頼し、その内容をもとにページ内のリンクを生成しているにもかかわらず、CDN がその Header の違いを区別していないケースです。改ざんされたページがキャッシュされると、後から訪れた正規の訪問者にも同じコンテンツが返される可能性があります。</p>
<p>対処方法はアプリケーションの要件に応じて決める必要があります。不要な入力の影響を取り除く、キャッシュポリシーでコンテンツを正しく区別する、あるいはそのレスポンスに共有キャッシュを使わせない、といった方法があります。</p>
<p><strong>Cache Key は複雑なほど良いわけではありません。</strong> すべての Cookie やパラメーターを含めると、再利用率の低いキャッシュバージョンが大量に生まれる可能性があります。また、本人確認や認可が関わるコンテンツは、キャッシュ項目を増やしただけで安全とみなすことはできません。</p>
<h2>キャッシュ設定で確認すべき情報とは？</h2>
<p>設定の前に、アプリケーションのパスごとに「どの情報がレスポンスを変えるのか」を整理し、そのうえで共有と除外のルールを決めることをおすすめします。</p>
<div class="table-wrap">
<table>
<thead>
<tr><th>リクエスト情報</th><th>確認すべきポイント</th><th>想定コンテンツと設定の方向性</th></tr>
</thead>
<tbody>
<tr><td>パス Path</td><td>公開リソース、会員ページ、取引エンドポイントのどれか？</td><td>商品画像は共有を検討できますが、アカウントや決済のコンテンツは共有キャッシュの利用を明確に制限すべきです。</td></tr>
<tr><td>Query String</td><td>パラメーターが言語、通貨、検索条件、アクセス権限に影響するか？</td><td>意味のあるコンテンツの違いは残します。トラッキング用パラメーターは、レスポンスに影響しないことを確認したうえで無視するかを検討します。</td></tr>
<tr><td>Cookie</td><td>会員価格、カート、パーソナライズ情報を変えるか？</td><td>公開コンテンツとパーソナライズされたコンテンツを分けて扱い、機密性の高いレスポンスが異なるユーザー間で共有されないようにします。</td></tr>
<tr><td>Header</td><td>言語選択、リダイレクト、コンテンツ生成に関わるか？誰が設定するのか？</td><td>必要な項目、信頼できる送信元、処理方法を確認し、クライアント側から渡されるプロキシ情報をそのまま信頼しないようにします。</td></tr>
<tr><td>想定コンテンツ</td><td>同じ条件のもとで、どの部分が一致すべきで、どの部分を分離すべきか？</td><td>本文、ステータスコード、レスポンス Header、リダイレクト先を含む、比較可能な受け入れ基準を設けます。</td></tr>
</tbody>
</table>
</div>
<p>オリジンのキャッシュ指示もあわせて確認が必要です。HTTP キャッシュの仕様では、private は共有キャッシュによるレスポンスの保存を制限し、no-store は保存しないことを求め、no-cache は保存を許可するものの再利用の前に検証を必要とします。この 3 つを混同してはいけません。</p>
<p>デプロイ時には、CDN のルールがオリジンの設定を上書きしていないかを確認し、Vary、Cookie、認可付きリクエストが実際にどう処理されるかもテストしましょう。ファイル名が静的リソースのように見えるというだけで、公開共有に適したコンテンツだと判断してはいけません。</p>
<h2>キャッシュ設定はどう検証すればよいのか？</h2>
<p>受け入れテストでは、パフォーマンスとコンテンツの正確性の両方を確認する必要があります。隔離されたテスト用ドメインや許可された環境で、テストアカウントと合成データを使い、次の 3 つの段階を順に比較することをおすすめします。</p>
<div class="table-wrap">
<table>
<thead>
<tr><th>検証段階</th><th>確認内容</th></tr>
</thead>
<tbody>
<tr><td>オリジンのレスポンス</td><td>言語、通貨、アカウントごとに、想定どおりのコンテンツが返されるか？</td></tr>
<tr><td>CDN の初回レスポンス</td><td>既存のキャッシュがないことを確認したうえで、オリジンから取得した結果が想定と一致するか？</td></tr>
<tr><td>その後のキャッシュヒット</td><td>別のセッションが受け取るコンテンツが、そのリクエスト条件に合っているか？</td></tr>
</tbody>
</table>
</div>
<p>1 回のテストで変える条件はひとつに絞ると、違いがどこから生じているのかを切り分けられます。本文だけでなく、ステータスコード、リダイレクト先、キャッシュ制御、プラットフォームが提供するキャッシュステータス情報も比較しましょう。</p>
<p>特に重要なのが、アカウントをまたいだ確認です。アカウント A が操作を終えた後に、アカウント B や未ログインの訪問者が A の個人情報を受け取ってはいけません。一方で、公開されていて共有が許可されたコンテンツは、正しいバージョンが維持されている必要があります。</p>
<p>つまり、<strong>HIT はキャッシュが使われたことを示すにすぎず、返されたコンテンツが正しいかどうかは別途確認が必要です。</strong> ブラウザと CDN で結果が異なる場合は、ブラウザのキャッシュも切り分けて調べ、問題の原因を取り違えないようにしましょう。</p>
<p>速度テスト、Response Header、キャッシュヒット率から CDN の実際のパフォーマンスを確認する方法については、<a href="/ja/blog/is-your-cdn-actually-working/">『CDN は本当に機能しているか？速度テストからキャッシュヒット率までのトラブルシューティング手順』</a>もあわせてご覧ください。</p>
<p>ポイズニングの発生を確認した場合は、まず影響を受けたキャッシュ動作を制限し、必要な記録を残します。根本原因を修正してから関連するキャッシュを削除し、再テストを行うことで、誤ったコンテンツが再び書き込まれるのを防ぎます。</p>

<h2>よくある質問</h2>
<h3>CDN キャッシュポイズニングとは何ですか？</h3>
<p>本来区別すべきリクエストを CDN が同じものとして扱うと、攻撃者はその判断のずれを突いて、改ざんされたレスポンスを共有キャッシュに入り込ませることができます。その結果、後から訪れた正規の訪問者にも同じコンテンツが返される可能性があります。これが CDN キャッシュポイズニング（Cache Poisoning）です。</p>
<h3>Cache Key は複雑なほど良いのですか？</h3>
<p>いいえ。すべての Cookie やパラメーターを含めると、再利用率の低いキャッシュバージョンが大量に生まれる可能性があります。また、本人確認や認可が関わるコンテンツは、キャッシュ項目を増やしただけで安全とみなすことはできません。まずはアプリケーションのパスごとに、どの情報がレスポンスを変えるのかを整理し、そのうえで共有と除外のルールを決めましょう。</p>
<h3>HIT と表示されていれば、キャッシュ設定は正しいと言えますか？</h3>
<p>必ずしもそうとは限りません。HIT が証明するのはキャッシュが使われたことだけで、返されたコンテンツが正しいかどうかは別途確認が必要です。検証では本文に加えて、ステータスコード、リダイレクト先、キャッシュ制御、プラットフォームが提供するキャッシュステータス情報も比較し、異なるアカウントや未ログインの訪問者がそれぞれ本来のコンテンツを受け取っているかを確認します。</p>
